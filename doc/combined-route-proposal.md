# 剧情与关卡 JSON 数据方案

本文把“扩展新剧情”的目标改为：**地图保持原始二进制，剧情和关卡逻辑导出为可读 JSON，并由 JSON 驱动运行时**。这不是把原资源粗暴转换成一份文件，而是保留原版地图／渲染／移动规则，同时把可扩展的数据边界从 `SUPERSP.BIN` 中抽出来。

## 1. 数据边界

### 1.1 地图不导出

地图仍由 `SUPERSP.PRG` 的原始连续数据提供，不生成地图 JSON：

- 地面、物件、高程和地图宽高保持原始二进制值；
- 地图目录、移动规则、地面／物件属性和动作资源继续经 `SUPERSP.PRG`／`SUPERSP.DAT` 读取；
- 关卡 JSON 只引用 `map_id`，不复制地图格数据；
- 新剧情优先复用已有地图。若确实需要新地图，仍须新增兼容原 PRG 目录和属性表的二进制地图资源。

这样可以避免把连续地形数据误解为“宝箱”或“剧情点”，也不会因 JSON 导出／回写改变原地图寻路结果。

### 1.2 关卡 JSON

每个可进入的阶段对应一个 JSON 文件，路径为资源根的 `json/stage-<stage-id>.json`。字段分为三层：

```json
{
  "stage": 140,
  "name": "可读关卡名称",
  "map_id": 12,
  "music": 3,
  "first_turn": 1,
  "units": [],
  "deployment": [],
  "objects": [],
  "briefing": "可读简报文字",
  "objectives": {
    "victory": "可读胜利目标",
    "defeat": "可读失败目标"
  },
  "events": []
}
```

- `units`：关卡固定的敌人和 NPC，保存角色 ID、外观／职业、初始坐标、行为、登场回合、属性、装备、能力和初始状态；
- `player_party`：不保存我方当前角色快照，只保存原关卡记录中的槽位／角色 ID与部署候选坐标，并标记实际来源为 `save.group[0].units`。进入关卡时，等级、经验、HP/MP、职业、能力、装备和库存必须从当前存档恢复；JSON 不能覆盖这些可变队伍数据；
- `arrival`：固定角色的登场回合范围；例如第1关刑天的 `first_turn=5` 表示第5回合才可用，不是对白事件临时生成。
- `deployment`：可部署点的 `x`、`y`、方向、角色限制和固定标记；
- `objects`：只记录已经由汇编和运行时确认的动态对象语义，例如物件坐标、类型、触发旗标、物品候选；未知字段保留数字，不按图片或物件编号猜成宝箱；
- `events`：事件类型、子条件、参数、完成旗标、对白／选择引用及其状态边界；
- `briefing`、`objectives`、`name`：直接使用 UTF-8 可读文字，不再要求调用方处理 `*_bytes`。

JSON 不复制 `SUPERSP.PRG` 地图格，也不把运行时临时字段（动画帧、路径缓存、瞬时效果状态）伪装成关卡数据。存档中的事件完成状态仍需单独保存，并按 `stage` 与事件 ID 校验。

### 1.3 剧情 JSON

剧情应独立于关卡文件，后续可放在 `json/story.json`。它描述阶段进入、对白、选择、旗标和阶段跳转；但对某个事件实际使用的对白，只在该阶段 JSON 的 `events[].lines` 中保存一次：

```json
{
  "stages": {
    "140": {
      "events": [
        {
          "index": 0,
          "type": 1,
          "lines": [
        { "speaker": 11, "name": "白志超", "text": "可读对白文字" }
          ]
        },
        {
          "index": 1,
          "type": 5,
          "lines": [
        { "id": "baizhichao", "text": "选择白志超" },
        { "id": "natalia", "text": "选择娜塔莉雅" },
        { "id": "new_route", "text": "第三路线" }
          ]
        }
      ],
      "branches": {
        "baizhichao": { "stage": 1 },
        "natalia": { "stage": 71 },
        "new_route": { "stage": 200 }
      }
    }
  }
}
```

文字字段使用 UTF-8；可选的 `name_bytes`／`text_bytes` 只能作为原资源审计信息，不能再作为新剧情的必填输入。显示层直接按 Unicode 字符测量、换行和逐字展开；原始 BIN 读取的文本则在导出边界统一通过 CP950／Big5 严格解码。

## 2. 第140阶段迁移

当前 [json/stage-140.json](../../json/stage-140.json)、[json/stage-1.json](../../json/stage-1.json) 和 [json/stage-2.json](../../json/stage-2.json) 是从原始 BIN 导出的阶段文件，包含阶段头、固定敌人/NPC、`player_party` 存档注入规则、装备、事件参数和对白；对白使用 UTF-8 `name`／`text`，不再有顶层 `dialogue`/`choices` 镜像。修改某个事件的对白只需修改该事件的 `lines`；第140阶段事件0为开场对白，事件1为选择提示和选项，其中第一条是原版提示行，后两条才是可选项。当前运行时已实际读取所有存在且合法的 `stage-<id>.json` 中的地图号、音乐号和事件对白；阶段路由 `route.next_stage` 与 `route.mode` 也已优先读取 JSON。固定单位模板、动态对象和存档队伍属性仍由原始战斗初始化路径提供，JSON 中的 `units` 尚不覆盖运行时单位快照。

村庄表已导出为 [towns.json](../../json/towns.json)。JSON 只保存源码已确认的村庄编号、UTF-8 名称、主地图坐标、服务开关和三个商店分类的物品编号；运行时通过共享解析器重建现有旅馆、商店和世界地图消费者所需的内部表，不保存原始字节转储。缺失时回退 `SUPERSP.BIN`，格式错误显式失败。白志超路线的第一个可用商店已核实为：阶段140选择白志超进入阶段1，阶段1结算进入村庄1（服务关闭），阶段2结算进入村庄2（服务开启、14个商品）。

导出器不会按数值统一删除 `0`：`id=0` 表示无固定角色编号，`behavior=0` 表示从存档注入的我方队伍，`condition=0` 表示无子条件，`last_turn=0` 表示持续到关卡结束，坐标和数组中的 `0` 也可能是有效值，均保留。只有对白行的 `music_before`／`music_after` 在值为 `0` 时省略，因为原语义是“不改变当前音乐”；读取方对缺失音乐字段按 `0` 处理。

事件不保存 `line_count`：有 `lines` 时直接使用数组长度，没有 `lines` 时视为没有对白行；这样避免计数与实际文本数组不一致。

事件 JSON 不使用无语义的通用 `flag`／`parameters`。已确认的类型按语义命名：类型1无条件回合事件写 `trigger.turn`；类型5/9写 `trigger_flag` 与 `operands.first/second/third`；类型3写 `role_id`。其他类型写 `raw_operands.offset_3/5/7/9` 并标记 `raw_operands_semantics: "unconfirmed"`，直到汇编核对完成后再改成具体字段。

1. 从第140阶段事件0导出9条对白；
2. 从事件1导出当前3条选择；
3. 通过现有 CP950／Big5 解码器生成 `name` 与 `text`；
4. 保留原 `speaker`、音乐参数、事件号和原始字节校验字段作为可选 `source` 信息；
5. 将第三项改为显式 `id` 和 `branches` 映射，不允许继续使用“非1值全部进入 alternate_stage”的二分逻辑。

JSON 缺失时可在过渡期回退原 BIN；JSON 存在但字段、编码或分支目标错误时必须显式失败。完成全部阶段导出并通过回归后，再关闭剧情和关卡的 BIN 回退，进入 JSON 主驱动模式。

## 3. 运行时迁移阶段

### 阶段 A：只读导出与校验

- 为168个原始阶段导出关卡 JSON，为所有事件保留原类型和参数；
- 导出所有角色、坐标、装备、部署点、动态对象链、简报和目标；
- 导出剧情文本为 UTF-8，并为每行保留来源阶段／事件／行号；
- 导出器必须能从 JSON 与原 BIN 做结构化 diff，未知字段报告为数字而不是猜测名称。

### 阶段 B：JSON 覆盖

- `Events` 优先加载对应阶段 JSON；
- 地图仍通过 `map_id` 加载原 PRG；
- 未覆盖字段继续读取 BIN，并在诊断中标明来源；
- 新增事件、角色和选择只允许在 JSON 覆盖层中增加，不能静默改变旧存档的事件数组长度。

### 阶段 C：JSON 主驱动

- 剧情文本、选择、旗标分支和阶段跳转全部来自 `story.json`；
- 关卡角色、部署、动态对象和事件全部来自阶段 JSON；
- BIN 只作为官方原始资源校验基线，不再作为运行时剧情输入；
- 旧存档按数据版本和阶段版本隔离，提供明确迁移或拒绝恢复路径。

## 4. 宝箱、部署点和敌人数据的规则

- **部署点**：可以直接从现有 `deployment_slots()` 导出，字段为坐标、方向、角色限制和固定标记。
- **强制出站**：`deployment[].fixed` 只表示该部署点是固定点，不等于角色必选。第1关白志超的原角色记录没有足够证据证明存在通用“必选角色”字段，因此 JSON 暂不伪造 `mandatory_role_ids`；他的属性和装备仍从当前存档读取。若要表达强制出站，必须先从序幕初始化和部署确认汇编确认具体规则，再填入 `deployment_rules.mandatory_role_ids`。
- **固定回合**：事件 `type=1`、`condition=0` 时，事件的原 `+3` 操作数导出为 `trigger.kind="turn"`、`trigger.turn`；第1关可见第1、4、5回合事件，刑天本身由单位 `arrival.first_turn=5` 控制。
- **敌人/NPC**：从 `units` 导出行为、坐标、登场回合、属性、装备和能力；不要把 `hostile()` 的运行时判断结果当作唯一原始字段，应同时保留原 `behavior`。我方行为为0的记录不进入 `units`，而进入 `player_party` 存档注入规则。
- **动态对象**：导出 `dynamic_object_chains` 及已核实的 `Battle::Cell.object` 语义；未知对象只保存 `object_id`／坐标／原始参数。
- **宝箱**：当前没有证实一个通用宝箱记录表或统一宝箱 opcode。只有在汇编确认触发函数、奖励物品、旗标和消耗顺序后，才在 JSON 中命名为 `chest`；此前只能使用 `objects`／`item_candidates` 等中性字段。
- **地图点位**：任何点位都引用地图坐标，不复制地图数据；坐标合法性由对应 PRG 地图边界校验。

## 5. 必须保持的原版约束

1. JSON 不能改变地图移动规则、地形属性、随机流、原事件挂起／消耗顺序和输入时序。
2. 原始资源中的 Big5 文本只在导出时解码；新增剧情直接使用 UTF-8，不再伪造 Big5 字节。
3. 事件完成状态、旗标、库存和角色成长属于存档状态，不能仅凭重新加载 JSON 推导覆盖。
4. 未确认的事件子条件、动态对象类型和宝箱语义必须保留数字并报告证据缺口。
5. 每个 JSON 阶段必须能通过原 BIN 对照测试：地图号、角色数、角色 ID、坐标、事件数、事件类型和原始文本行数先逐项一致，再允许扩展字段。

## 6. 当前结论

这个方向可行，而且比继续扩展第140阶段的字节覆盖更适合自由添加剧情：地图作为稳定的二进制底座，剧情／关卡作为可版本化的 JSON 数据，新增文本直接使用可读 UTF-8。当前工程还处于阶段 A 与阶段 B 之间，尚未完成168个阶段的导出器、UTF-8 渲染入口、JSON 关卡加载器和存档版本迁移；因此不能把现有开场 JSON 覆盖称为“全部 JSON 驱动”。
